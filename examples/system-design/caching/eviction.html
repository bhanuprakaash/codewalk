Eviction and expiry

A cache is smaller than the data behind it, and data goes out of date. Two different mechanisms handle this: eviction removes keys because memory is full, and expiry removes keys because their time is up. Back to the caching overview.

1Eviction policies

When the cache is full and a new key arrives, something has to go. The policy decides what.

PolicyEvictsGood atWeak at
LRU least recently usedThe key untouched longestMost workloads; recent use predicts near-future useA one-time scan of many keys pushes out the hot ones
LFU least frequently usedThe key with the fewest accessesStable popularity, scan resistanceOld popular keys linger unless counts decay
FIFOThe oldest inserted keySimplicityIgnores use; can evict the hottest key
RandomAny keyAlmost no bookkeepingNo intelligence at all

2LRU, worked example

A cache with 3 slots and the access sequence A B C A D B. The list is ordered most recent first; the last item is next to be evicted.

# cache: most recent → least recent
access result           cache
  A    miss             [A]
  B    miss             [B A]
  C    miss             [C B A]
       # full
  A    hit              [A C B]
       # A moves to the front
  D    miss, evict B    [D A C]
       # B was least recent
  B    miss, evict C    [B D A]
       # C was least recent

1 hit in 6 accesses. A was saved because it was touched again before D arrived. With FIFO, the fourth access would not have protected A, and D would have evicted A instead of B.

Eviction can remove a key that is still valid. A later request for it is simply a miss. An evicted key and an expired key look identical to the reader.

3TTL and expiry

A TTL (time to live) is a per-key deadline: SET key value EX 300 or EXPIRE key 300. After it passes, the key must no longer be returned. It bounds staleness and clears out data nobody asks for.

Scanning every key every second would be too expensive, so Redis combines two strategies:

  • Lazy expiry: when a key is accessed, Redis checks its deadline first and deletes it if it has passed. A reader never sees an expired key.
  • Active expiry: several times per second Redis samples a batch of keys that have a TTL, deletes the expired ones, and repeats if a large share of the sample was expired.
every ~100 ms:
  pick 20 random keys with a TTL
  delete the expired ones
  if more than 25% were expired: repeat
  # bounded by a time budget

Lazy expiry alone would leak memory from keys never read again; active expiry alone could leave expired keys visible between sweeps. Together they are cheap and correct from the reader's view, though expired keys can occupy memory for a while.

4Redis settings

Eviction only starts when memory reaches maxmemory. The maxmemory-policy setting picks the rule:

PolicyCandidatesRule
noevictionnoneWrites that need memory fail with an error; reads still work. The default.
allkeys-lruall keysEvict the least recently used. The usual choice for a pure cache.
allkeys-lfuall keysEvict the least frequently used.
allkeys-randomall keysEvict a random key.
volatile-lrukeys with a TTLLeast recently used among keys that have an expiry.
volatile-lfukeys with a TTLLeast frequently used among keys that have an expiry.
volatile-randomkeys with a TTLRandom among keys that have an expiry.
volatile-ttlkeys with a TTLEvict the key with the shortest remaining TTL.

The volatile-* policies never touch keys without a TTL. If none are eligible, they behave like noeviction and writes fail. Use them when the same Redis holds both cache entries (with TTLs) and data that must stay (without).

Redis LRU is approximate. A true LRU needs a linked list updated on every read, which is costly. Instead Redis keeps a small last-access clock on each key and, when it must evict, samples a few random keys and removes the one idle longest. maxmemory-samples sets the sample size; the default is 5, 10 is closer to true LRU, and higher costs more CPU. LFU is also approximate: it keeps a small logarithmic counter that decays over time, tunable with lfu-log-factor and lfu-decay-time.

# redis.conf
maxmemory 4gb
maxmemory-policy allkeys-lru
maxmemory-samples 10

# watch it
INFO stats
# evicted_keys, expired_keys,
# keyspace_hits, keyspace_misses

The map's last flow, "Cache full · LRU eviction", plays this on a 3-key cache so you can see which key goes and why.

5Jitter

If a thousand keys are loaded together with the same 300 s TTL, they all expire together, and the database takes a thousand misses in the same moment. This happens after a deploy, a cache restart or a bulk load. The fix is to randomize the TTL a little:

# spread expiry across a minute
ttl = 300 + random(0, 60)
SET user:42 val EX ttl

Jitter spreads many keys. For one very hot key you also need a lock or single-flight on refill, as in the stampede flow on the map.

Summary

  • Eviction is for memory pressure; expiry is for time. Both look like a miss to the reader.
  • LRU is the sensible default; LFU resists scans; FIFO and random are cheap and blunt.
  • Redis expires keys lazily on access and by periodic sampling.
  • Pure cache: allkeys-lru with a sized maxmemory. Mixed data: a volatile-* policy.
  • Redis LRU samples keys, so it is approximate; raise maxmemory-samples for accuracy.
  • Add TTL jitter so keys do not expire together. Back to the overview.
