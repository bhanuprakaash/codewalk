Caching

A cache keeps a copy of data in something faster than where it normally lives. Done well, it removes most of your database load and most of your latency. Done badly, it serves wrong answers quickly. This page covers why, where, and how; the Map tab lets you play every flow step by step.

1Why cache at all

Different storage layers differ by orders of magnitude in access time. The numbers below are rough, but the ratios are what matter.

OperationTypical timeRelative
Read from process memory~100 ns1x
Redis round trip, same datacenter0.2 to 0.5 ms~2,000 to 5,000x
SSD random read~0.1 ms~1,000x
Database query, indexed lookup1 to 10 ms~10,000 to 100,000x
Database query under load, joins, cold pages10 to 100+ msfar more
Cross-continent round trip~150 ms~1,500,000x

Notice that even a fast distributed cache is dominated by the network round trip, not the memory access. It is still 5 to 50 times quicker than a database query. The second benefit is capacity: if 95% of reads are answered by the cache, the database serves one request in twenty, so a database that was at its limit now has room to grow.

A cache works because of skew. A small share of keys (popular users, hot products, today's front page) receives most of the reads. Caching that small hot set captures most of the benefit.

2Where caches live

A request can pass through many caches. Each one is closer to the user than the last, and each one adds a place for data to be stale.

This page and the map focus on the distributed cache, because it is the one you design. The same ideas (key, TTL, eviction, invalidation) apply at every layer.

3Hit ratio and average latency

The hit ratio is hits divided by total lookups. Average latency is a weighted mix of the fast and the slow path:

avg = hit_ratio × t_hit
    + (1 − hit_ratio) × t_miss

# t_hit  ≈ 1 ms (Redis path)
# t_miss ≈ 14 ms
#   (Redis GET + SELECT + SET)
hit ratio 50%:
  0.50 × 1 + 0.50 × 14 = 7.5  ms
hit ratio 90%:
  0.90 × 1 + 0.10 × 14 = 2.3  ms
hit ratio 95%:
  0.95 × 1 + 0.05 × 14 = 1.65 ms
hit ratio 99%:
  0.99 × 1 + 0.01 × 14 = 1.13 ms

The same ratio governs database load. At 10,000 reads per second:

hit ratio 90% → 1,000 queries/s
                reach the database
hit ratio 95% →   500 queries/s
hit ratio 99% →   100 queries/s

Going from 90% to 99% looks like a small gain, but it cuts database load tenfold. Look at the miss ratio, not the hit ratio, when sizing the database. This is also why a cache outage hurts so much: 95% to 0% multiplies database load by twenty.

Redis reports keyspace_hits and keyspace_misses in INFO stats. Watch them, together with evicted_keys. A falling hit ratio with rising evictions means the cache is too small for your working set.

4Read patterns

Cache-aside (lazy loading)

The application manages the cache itself. It checks the cache, and on a miss loads from the database and stores the result. Only data that is actually requested is cached, and a cache failure just means misses.

def get_user(id):
    # 1. ask the cache
    v = redis.get(f"user:{id}")
    if v is not None:
        return decode(v)  # hit
    # 2. miss: read truth
    row = db.query(
        "SELECT * FROM users"
        " WHERE id = %s", id)
    # 3. fill, with a TTL
    redis.set(f"user:{id}", encode(row),
              ex=300)
    return row
client ─► app ─► Redis
  hit  ─► reply                  (~1 ms)
  miss ─► Postgres ─► app ─► SET
       ─► reply                 (~14 ms)

Read-through

The cache itself loads missing data. The application only talks to the cache, and the cache has a loader function (or sits in front of the database as a library, a proxy or a managed service). The flow is the same as cache-aside, but the logic lives in one place instead of in every caller. Plain Redis does not do this; libraries and some products do.

Cache-aside is the default with Redis. Its cost is that every caller must remember the pattern, and the first request after expiry always pays the miss.

5Write patterns

# write-through:
# app writes cache and DB together
app ─► cache ─► DB
# write completes after both

# write-behind (write-back):
# DB is updated later
app ─► cache ─ ack ─► app   # fast ack
          └── (async, batched) ─► DB

# write-around: skip the cache on write
app ─► DB
# cache filled on the next read
PatternWrite latencyRead after writeRisk
Write-throughSlower: two writes in the pathAlways freshCaches data that may never be read; the two writes can still disagree if one fails
Write-behindFastest: ack from memoryFresh from the cacheData loss if the cache dies before flushing; ordering and retry complexity
Write-aroundNormal DB writeFirst read missesStale if an old copy already exists and is not invalidated
Cache-aside + invalidateDB write plus one DELFirst read misses, then freshSmall race windows (see below)

Write-behind is the one to be careful with: while data sits only in the cache, the cache is the source of truth, and a crash loses it. Use it for data you can afford to lose (counters, view counts), or with a durable log underneath.

6Invalidation

"There are only two hard things in computer science: cache invalidation and naming things." When the database changes, the cached copy must go. You have two choices.

  • Update on write: write the new value into the cache after the DB write.
  • Delete on write: remove the key and let the next read reload it. Usually preferred.

Why delete wins: with update-on-write, two writers can interleave so the cache ends up with the older value. Writer A updates the DB to v1, writer B updates it to v2, but B's cache write lands first and A's lands last. The DB says v2, the cache says v1, and nothing will fix that until the TTL. A delete has no such order problem: whoever deletes last, the key is gone, and the next reader fetches whatever the database says. Update-on-write also caches values that may never be read, and may require recomputing derived objects.

update on write
  A: DB=v1
  B: DB=v2
  B: SET cache=v2
  A: SET cache=v1  ← stale until TTL

delete on write
  A: DB=v1
  B: DB=v2
  B: DEL key
  A: DEL key  ← cache empty, correct

Even delete-on-write has a race. A reader that misses can read the old row, stall, and write it into the cache after the writer's delete has already run:

reader: GET → miss
reader: SELECT (sees v1)
writer: UPDATE → v2
writer: DEL key (nothing there)
reader: ·········► SET cache=v1
result: cache holds v1, DB has v2

It is rare, because it requires a reader slower than a writer, but at scale it will happen. Defenses:

  • TTL as a safety net. Every key gets an expiry (SET key val EX 300), so even a missed invalidation heals itself. Pick the TTL by how stale the data may be.
  • Delayed double delete: delete again after a short delay, longer than a slow read.
  • Versioned values: store the row version and only overwrite with a newer one.
  • CDC-driven invalidation: delete from the database's change log, with retries, so no code path can forget.

Order matters: write the database first, then delete the key. Deleting first lets a concurrent reader refill the old value before the new one is committed. The map has this as a what-if on the write flow.

7Consistency caveats

A cache makes your system eventually consistent at best. Three things to keep in mind:

  • Staleness is bounded by the TTL. If you cache for 5 minutes, someone will see a 5-minute-old value in the worst case. Decide that number on purpose.
  • Read your own writes. A user who edits their profile and reloads expects to see the change. Delete-on-write gives this for the writing path; with replicas or a CDN in between, it can break.
  • Multiple layers multiply staleness. A browser cache over a CDN over Redis can each add its own delay.

Some data should not be cached at all: balances being decremented, inventory counts at checkout, anything where a stale read causes a wrong action rather than a slightly old page. For those, read the database, or use the cache only as a hint and re-check at commit time.

The cache also adds failure modes: stampedes when a hot key expires, outages that shift all load onto the database, and cold starts. All three are flows on the map.

Summary

  • Caches exist for latency and for protecting the database; look at the miss ratio to size the database.
  • Cache-aside is the default: GET, on miss SELECT then SET with a TTL.
  • On writes, update the database first, then delete the key; do not update the cache.
  • Always set a TTL. It bounds staleness when invalidation fails or races.
  • Plan for the cache being gone: tight timeouts, a circuit breaker, and a database that survives the extra load.
